# ডেটাবেস Stored Procedures (সহজ গাইড)

এই ফাইলে 4টি Stored Procedure খুব সহজ এবং সাধারণ বাংলায় বুঝিয়ে দেওয়া হলো।

---

# 1. `sp_AddOwner`

## সহজ কথায় এর আসল কাজ কী?
নতুন দোকান মালিক (Owner) তৈরি করা। শুধুমাত্র চালু থাকা Admin (সক্রিয় অ্যাডমিন) নতুন Owner যোগ করতে পারবে। 
1. প্রথমে `owners` টেবিলে তথ্য ঢুকবে এবং সেখান থেকে নতুন `ownerid` তৈরি হবে।
2. এরপর সেই `ownerid` দিয়ে `users` টেবিলে ওই Owner-এর লগইন অ্যাকাউন্ট তৈরি হবে।

Owner-এর অ্যাকাউন্ট তৈরির সময় পাসওয়ার্ড সুরক্ষিতভাবে হ্যাশ (Bcrypt) করে রাখা হবে এবং `refreshtoken` শুরুতে খালি স্ট্রিং (`''`) থাকবে। Owner প্রথমবার সফলভাবে লগইন করলে ব্যাকএন্ড থেকে টোকেন জেনারেট করে বসিয়ে দেওয়া হবে।
দুটি টেবিলেই ইনসার্ট একসাথে হবে—অর্থাৎ `users` টেবিলে কোনো কারণে তথ্য না ঢুকলে `owners` টেবিলের ডেটাও স্বয়ংক্রিয়ভাবে মুছে যাবে (Rollback হবে)।

---

## কল করার নিয়ম (Calling Query)

```sql
CALL public.sp_add_owner(
    1,                                 -- p_admin_user_id (অ্যাডমিনের আইডি)
    'Rahul Das',                       -- p_fullname (মালিকের নাম)
    'rahul@example.com',               -- p_email (ইমেইল)
    'Rahul@1234',                      -- p_password (পাসওয়ার্ড)
    '9876543210',                      -- p_phone (ফোন নম্বর, না থাকলে NULL)
    'Kolkata, WB',                     -- p_address (ঠিকানা, না থাকলে NULL)
    5,                                 -- p_max_shop_count (সর্বোচ্চ দোকান সংখ্যা)
    NULL,                              -- p_backup_id (ব্যাকআপ আইডি, অপশনাল)
    NULL,                              -- OUT: p_status_code
    NULL,                              -- OUT: p_status_message
    NULL,                              -- OUT: p_new_owner_id
    NULL                               -- OUT: p_new_user_id
);
```

---

## ইনপুট তালিকা (Inputs)

| ইনপুট প্যারামিটার | ডেটা টাইপ | সহজ বিবরণ |
| :--- | :--- | :--- |
| `p_admin_user_id` | `INTEGER` | যে অ্যাডমিন Owner যোগ করছে তার User ID |
| `p_fullname` | `VARCHAR` | Owner-এর পুরো নাম |
| `p_email` | `VARCHAR` | Owner-এর ইমেইল (অবশ্যই ইউনিক হতে হবে) |
| `p_password` | `TEXT` | Owner-এর লগইন পাসওয়ার্ড |
| `p_phone` | `VARCHAR` | মোবাইল নম্বর (না দিলেও চলবে / Optional) |
| `p_address` | `TEXT` | ঠিকানা (না দিলেও চলবে / Optional) |
| `p_max_shop_count` | `INTEGER` | এই Owner সর্বোচ্চ কয়টি দোকান খুলতে পারবে (1 থেকে 5) |
| `p_backup_id` | `INTEGER` | ব্যাকআপ আইডি (না দিলেও চলবে / Optional) |

---

## আউটপুট তালিকা (Outputs)

| আউটপুট প্যারামিটার | ডেটা টাইপ | সহজ বিবরণ |
| :--- | :--- | :--- |
| `p_status_code` | `TEXT` | কাজের রেজাল্ট কোড (যেমন: `SUCCESS`, `ERR_...`) |
| `p_status_message` | `TEXT` | কাজের বিস্তারিত মেসেজ |
| `p_new_owner_id` | `INTEGER` | নতুন তৈরি হওয়া Owner ID |
| `p_new_user_id` | `INTEGER` | নতুন তৈরি হওয়া User ID |

---

## সম্ভাব্য রেজাল্ট (Possible Outputs)

| আউটপুট কোড | আসল অর্থ |
| :--- | :--- |
| `SUCCESS` | Owner সফলভাবে তৈরি হয়েছে |
| `ERR_INVALID_ADMIN` | অ্যাডমিনের User ID সঠিক নয় বা পাওয়া যায়নি |
| `ERR_UNAUTHORIZED` | চালু অ্যাডমিন ছাড়া অন্য কেউ Owner তৈরি করার চেষ্টা করেছে |
| `ERR_REQUIRED_FIELDS` | নাম, ইমেইল বা পাসওয়ার্ডের মতো জরুরি তথ্য দেওয়া হয়নি |
| `ERR_DUPLICATE_EMAIL` | এই ইমেইল দিয়ে আগেই অন্য একাউন্ট খোলা আছে |
| `ERR_INVALID_SHOP_COUNT` | দোকানের সংখ্যা অবশ্যই 1 থেকে 5-এর মধ্যে হতে হবে |
| `ERR_DUPLICATE` | অন্য কোনো ইউনিক তথ্য আগেই ডেটাবেসে আছে |
| `ERR_FOREIGN_KEY` | রেফারেন্স করা কোনো তথ্য পাওয়া যায়নি |
| `ERR_SYSTEM` | ডেটাবেসে অন্য কোনো অপ্রত্যাশিত সমস্যা হয়েছে |

---

## জরুরি নিয়ম ও বিষয়সমূহ

- **শুধু চালু Admin:** ইউজারের `roleid = 1` এবং `status = TRUE` থাকলেই কেবল কাজ হবে।
- **নির্দিষ্ট Role:** নতুন Owner-এর `roleid` সবসময় `2` হবে।
- **পাসওয়ার্ড নিরাপত্তা:** পাসওয়ার্ড সরাসরি প্লেইন টেক্সট হিসেবে সেভ হবে না, `crypt()` দিয়ে হ্যাশ হয়ে থাকবে।
- **রিফ্রেশ টোকেন:** অ্যাকাউন্ট তৈরির সময় `refreshtoken = ''` (খালি স্ট্রিং) থাকবে।
- **ডিফল্ট মান:** নতুন Owner-এর `isemailverified = FALSE` এবং `status = TRUE` থাকবে।
- **দোকানের লিমিট:** 1টির কম বা 5টির বেশি দোকান দেওয়া যাবে না।

# 2. `sp_UpdateUser`

## সহজ কথায় এর আসল কাজ কী?
আগে থেকে থাকা ইউজারের সাধারণ ব্যক্তিগত তথ্য (যেমন নাম, ফোন নম্বর, প্রোফাইল ছবি ইত্যাদি) পরিবর্তন করা।

## কল করার নিয়ম

```sql
CALL public.sp_update_user(
    10,                         -- User ID
    'Rahul Jana',               -- Full Name
    '9876543210',               -- Phone
    'profile-image-url',        -- Profile Image
    NULL,                       -- OUT: Status Code
    NULL                        -- OUT: Status Message
);
```

## ইনপুট
- **User ID** (কার তথ্য বদলাবে)
- **Full Name** (নতুন নাম)
- **Phone Number** (নতুন ফোন নম্বর - অপশনাল)
- **Profile Image** (নতুন ছবির লিংক - অপশনাল)

## সম্ভাব্য রেজাল্ট
- `SUCCESS` – তথ্য সফলভাবে আপডেট হয়েছে।
- `ERR_INVALID_USER` – User ID ঠিক নেই।
- `ERR_USER_NOT_FOUND` – এই আইডি দিয়ে কাউকে খুঁজে পাওয়া যায়নি।
- `ERR_INVALID_NAME` – নাম ফাঁকা রাখা যাবে না।
- `ERR_SYSTEM` – ডেটাবেসে কোনো সমস্যা হয়েছে।

## জরুরি নিয়ম
- ইমেইল, পাসওয়ার্ড, রোল আইডি বা ওনার আইডি এই প্রসিডিউর দিয়ে বদলানো যাবে না।
- তথ্য আপডেট হলে `updatedat` ফিল্ডে বর্তমান সময় স্বয়ংক্রিয়ভাবে বসে যাবে।

# 3. `sp_UpdateOwnerStatus`

## সহজ কথায় এর আসল কাজ কী?
কোনো Owner-এর অ্যাকাউন্ট সাময়িকভাবে বন্ধ (Inactive / `FALSE`) বা চালু (Active / `TRUE`) করা। এই কাজ শুধু অ্যাডমিন করতে পারবে।

## কল করার নিয়ম

```sql
CALL public.sp_update_owner_status(
    1,       -- Admin User ID
    10,      -- Owner ID
    FALSE,   -- New Status (TRUE দিলে চালু, FALSE দিলে বন্ধ)
    NULL,    -- OUT: Status Code
    NULL     -- OUT: Status Message
);
```

## ইনপুট
- **Admin User ID** (যে অ্যাডমিন বন্ধ বা চালু করছে)
- **Owner ID** (যাকে বন্ধ বা চালু করা হবে)
- **New Status** (`TRUE` অথবা `FALSE`)

## সম্ভাব্য রেজাল্ট
- `SUCCESS` – সফলভাবে স্ট্যাটাস পরিবর্তন হয়েছে।
- `ERR_UNAUTHORIZED` – অ্যাডমিন ছাড়া অন্য কেউ চেষ্টা করেছে।
- `ERR_OWNER_NOT_FOUND` – এই Owner-কে খুঁজে পাওয়া যায়নি।
- `ERR_SYSTEM` – ডেটাবেসে কোনো সমস্যা হয়েছে।

## জরুরি নিয়ম
- Owner-এর অ্যাকাউন্ট Inactive হলে সে আর লগইন করে কোনো কাজ করতে পারবে না।
- `owners` এবং সংশ্লিষ্ট `users` টেবিল উভয়ের স্ট্যাটাস একসাথে বদলে যাবে।

# 4. `sp_DeleteOwner`

## সহজ কথায় এর আসল কাজ কী?
কোনো Owner-কে ডেটাবেস থেকে একবারে মুছে ফেলা (Delete করা)। এটিও শুধু একজন অ্যাডমিন করতে পারবে।

> **শর্ত:** যদি ওই Owner-এর নামে কোনো দোকান (Shop) খোলা থাকে, তবে তাকে ডিলিট করা যাবে না। আগে দোকান ডিলিট করতে হবে, তারপর Owner ডিলিট হবে।

## কল করার নিয়ম

```sql
CALL public.sp_delete_owner(
    1,       -- Admin User ID
    10,      -- Owner ID
    NULL,    -- OUT: Status Code
    NULL     -- OUT: Status Message
);
```

## ইনপুট
- **Admin User ID** (যে ডিলিট করছে)
- **Owner ID** (যাকে ডিলিট করা হবে)

## সম্ভাব্য রেজাল্ট
- `SUCCESS` – Owner সফলভাবে ডিলিট হয়েছে।
- `ERR_UNAUTHORIZED` – শুধু সক্রিয় অ্যাডমিন ডিলিট করতে পারবে।
- `ERR_OWNER_NOT_FOUND` – এই আইডি দিয়ে কোনো Owner নেই।
- `ERR_OWNER_HAS_SHOPS` – এই Owner-এর অধীনে দোকান আছে, তাই ডিলিট হবে না।
- `ERR_SYSTEM` – ডেটাবেসে কোনো সমস্যা হয়েছে।

## জরুরি নিয়ম
- প্রথমে `users` টেবিল থেকে এবং পরে `owners` টেবিল থেকে রেকর্ড ডিলিট হবে।
- কোনো একটি অংশ ডিলিট হতে সমস্যা হলে পুরো কাজটি আগের অবস্থায় ফিরে আসবে (Rollback হবে)।

# `sp_create_shop` (Shop Create Stored Procedure - Updated)

## 1. SP-এর actual কাজটা কী?

নতুন দোকান (Shop) তৈরি করে `public.shops` টেবিলে সেভ করার জন্য এই Stored Procedure ব্যবহার করা হয়। সরাসরি ডেটা ইনসার্ট করার আগে এটি বেশ কিছু জরুরি নিয়ম যাচাই (Validate) করে নেয়:

1. **Owner ID** সঠিক (`> 0`) কি না এবং সেই Owner ডেটাবেসে আসলেই আছে (exist করে) কি না তা check করে।
2. যে ইউজার রিকোয়েস্ট পাঠিয়েছে, তার **User ID** ঠিক (`> 0`) আছে কি না দেখে।
3. ইউজারটি **Active** (`status = TRUE`), তার **Role ID `2` (Owner)**, এবং সে ওই নির্দিষ্ট **Owner-এর অধীনে** আছে কি না তা verify করে।
4. দোকানের দরকারি তথ্যগুলো—যেমন **Shop Name**, **Address**, এবং **City** ফাঁকা (`NULL` বা খালি স্ট্রিং) আছে কি না তা চেক করে।
5. **Duplicate Shop Name Check:** একই Owner-এর অধীনে আগে থেকেই ওই নামে কোনো দোকান আছে কি না তা যাচাই করে (বড় বা ছোট হাতের অক্ষরের পার্থক্য থাকলেও আটকে দেবে)।
6. **Time Validation:** `openingtime` এবং `closingtime` দেওয়া থাকলে বন্ধ হওয়ার সময় খোলার সময়ের পরের কি না তা চেক করে।
7. সব ঠিক থাকলে `public.shops` টেবিলে নতুন দোকানের তথ্য ইনসার্ট করে (এখানে `shops` টেবিল থেকে `userid` কলামটি বাদ দেওয়া হয়েছে), শুরুতেই দোকানটি চালু (`isactive = TRUE`) রাখে এবং `createdat` ও `updatedat`-এ বর্তমান সময় বসিয়ে দেয়।
8. সফলভাবে দোকান তৈরি হলে নতুন তৈরি হওয়া **`shopid`** সহ `Status Code` এবং `Status Message` আউটপুট হিসেবে রিটার্ন করে।

---

## 2. SP Calling Query

```sql
CALL public.sp_create_shop
(
    1,                          -- p_owner_id (Owner ID)
    3,                          -- p_user_id (User ID)
    'Debo Technology Store',    -- p_shop_name (Shop Name)
    'Computer accessories',     -- p_description (Description)
    'Park Street',              -- p_address (Address)
    'Kolkata',                  -- p_city (City)
    'West Bengal',              -- p_state (State)
    '700016',                   -- p_pincode (Pincode)
    '9876543210',               -- p_phone (Phone)
    'shop@gmail.com',           -- p_email (Email)
    NULL,                       -- p_shop_image (Shop Image URL/Path)
    '09:30:00',                 -- p_opening_time (Opening Time)
    '21:30:00',                 -- p_closing_time (Closing Time)

    NULL,                       -- OUT: p_shop_id
    NULL,                       -- OUT: p_status_code
    NULL                        -- OUT: p_status_message
);
```

---

## 3. Inputs (IN Parameters)

এই প্রসিডিউরে মোট **13টি Input Parameter** দিতে হয়:

| Parameter | Data Type | সহজ বিবরণ (Description) | উদাহরণ (Example) |
| :--- | :--- | :--- | :--- |
| `p_owner_id` | `INTEGER` | যে Owner-এর অধীনে দোকান তৈরি হবে তার ID | `1` |
| `p_user_id` | `INTEGER` | দোকান তৈরির রিকোয়েস্ট পাঠানো User-এর ID (Validation-এর জন্য) | `3` |
| `p_shop_name` | `VARCHAR` | দোকানের নাম (Required & Unique per Owner) | `'Debo Technology Store'` |

## 5. Any Critical Scenario (গুরুত্বপূর্ণ ও জটিল বিষয়সমূহ)

* **Logical Time Check:** `p_opening_time` এবং `p_closing_time` উভয়ই দেওয়া থাকলে বন্ধ হওয়ার সময় অবশ্যই খোলার সময়ের চেয়ে বেশি হতে হবে (`p_opening_time < p_closing_time`)। কোনো একটি বা দুটিই `NULL` দিলে এই চেকটি স্কিপ করবে।
* **No `userid` Column in `shops` Table:** `shops` টেবিল থেকে `userid` কলামটি ড্রপ করা হয়েছে। তাই `p_user_id` শুধু ইউজার ভ্যালিডেশনের জন্য ইনপুট নেওয়া হয়, টেবিলে আর ইনসার্ট হয় না।
* **Default Active Status:** নতুন দোকান তৈরি হওয়ার সাথে সাথে সেটি স্বয়ংক্রিয়ভাবে চালু (`isactive = TRUE`) অবস্থায় ডেটাবেসে সেভ হয়।

# `sp_update_shop` (Shop Update Stored Procedure - Updated)

## 1. SP-এর actual কাজটা কী?

আগে থেকে থাকা কোনো দোকানের (Shop) তথ্য নিরাপদে আপডেট করার জন্য এই Stored Procedure ব্যবহার করা হয়। ডেটা পরিবর্তনের আগে এটি নিচের ধাপগুলো যাচাই (Validate) করে নেয়:

1. **Shop ID**, **Owner ID**, এবং **User ID** সঠিক (`> 0`) কি না তা check করে।
2. ওই **Owner** ডেটাবেসে আসলেই আছে কি না তা যাচাই করে।
3. ইউজারটি **Active** (`status = TRUE`), তার **Role ID `2` (Owner)**, এবং সে ওই নির্দিষ্ট **Owner-এর অধীনে** আছে কি না তা verify করে।
4. **Ownership Check:** প্রদত্ত `shopid` আসলেই ওই `ownerid`-এর অধীনে আছে কি না তা নিশ্চিত করে, যাতে এক মালিক অন্য মালিকের দোকান বদলাতে না পারে।
5. আবশ্যক ফিল্ডগুলো (**Shop Name**, **Address**, এবং **City**) ফাঁকা আছে কি না তা চেক করে।
6. **Duplicate Shop Name Check:** নাম পরিবর্তন করার সময় ওই Owner-এর অন্য কোনো দোকানের সাথে নাম মিলে যাচ্ছে কি না (`shopid <> p_shop_id`) তা চেক করে।
7. **Time Validation:** `openingtime` এবং `closingtime` দেওয়া থাকলে বন্ধ হওয়ার সময় খোলার সময়ের পরের কি না তা যাচাই করে।
8. **Safe Partial Update (`COALESCE`):** অপশনাল ফিল্ডগুলোতে `NULL` পাঠালেও আগের সেভ করা ডেটা মুছে না গিয়ে অপরিবর্তিত থাকে। সবশেষে `updatedat` আপডেট করে `Status Code` এবং `Status Message` রিটার্ন করে।

# `sp_delete_shop` (Shop Delete / Deactivate Stored Procedure)

## 1. SP-এর actual কাজটা কী?

কোনো দোকানকে (Shop) ডেটাবেস থেকে পুরোপুরি মুছে না ফেলে নিরাপদে **Soft Delete** (অর্থাৎ নিষ্ক্রিয় বা Deactivate) করার জন্য এই Stored Procedure ব্যবহার করা হয়। এতে দোকানের পুরনো রেকর্ড ও ডেটা সুরক্ষিত থাকে, কিন্তু সিস্টেমে দোকানটি আর সক্রিয় দেখায় না। কাজটি করার আগে এটি ধাপে ধাপে নিচের বিষয়গুলো যাচাই (Validate) করে নেয়:

1. **Shop ID** এবং **Owner ID** সঠিক (`> 0`) কি না তা check করে।
2. ওই **Owner** ডেটাবেসে আসলেই আছে (exist করে) কি না তা যাচাই করে।
3. যে ইউজার রিকোয়েস্ট পাঠিয়েছে, সে **Active** (`status = TRUE`), তার **Role ID `2` (Owner)**, এবং সে ওই নির্দিষ্ট **Owner-এর অধীনে** আছে কি না তা verify করে।
4. **Ownership Check:** প্রদত্ত `shopid` আসলেই ওই `ownerid`-এর অধীনে আছে কি না তা নিশ্চিত করে, যাতে এক মালিক অন্য মালিকের দোকান বন্ধ করতে না পারে।
5. **Active Status Check:** দোকানটি বর্তমানে চালু (`isactive = TRUE`) আছে কি না তা দেখে—যদি আগে থেকেই নিষ্ক্রিয় (`isactive = FALSE`) থাকে, তবে অযথা আপডেট না করে মেসেজ রিটার্ন করে।
6. সব ঠিক থাকলে `public.shops` টেবিলে ওই দোকানের `isactive = FALSE` এবং `updatedat`-এ বর্তমান সময় বসিয়ে দেয় এবং `Status Code` ও `Status Message` রিটার্ন করে।

| `p_status_message` | `VARCHAR` | কাজটি সফল হলো না কেন ব্যর্থ হলো তার বিস্তারিত মেসেজ |

## 5. Any Critical Scenario (গুরুত্বপূর্ণ ও জটিল বিষয়সমূহ)

* **Soft Delete vs Hard Delete:** এই প্রসিডিউরটি টেবিল থেকে রো (`ROW`) মুছে ফেলে না, বরং `isactive = FALSE` করে দেয়। ফলে ভবিষ্যতে ওই দোকানের পুরনো বুকিং, কিউ (Queue) হিস্ট্রি বা অডিট রিপোর্ট দেখতে কোনো সমস্যা হবে না।
* **Idempotency (একই রিকোয়েস্ট বারবার এলে):** যদি কোনো দোকান ইতিমধ্যেই নিষ্ক্রিয় (`isactive = FALSE`) অবস্থায় থাকে এবং ইউজার আবার সেটিকে ডিলিট করার রিকোয়েস্ট পাঠায়, তবে প্রসিডিউরটি `Shop is already inactive.` মেসেজ দিয়ে সেটি আটকে দেবে এবং `updatedat` টাইমস্ট্যাম্প অযথা পরিবর্তন করবে না।
* **Cross-Owner Protection:** এক Owner যেন কোনোভাবেই অন্য Owner-এর `shopid` দিয়ে দোকান বন্ধ করতে না পারে, তার জন্য `WHERE shopid = p_shop_id AND ownerid = p_owner_id` কন্ডিশনটি কঠোরভাবে ব্যবহার করা হয়েছে।
* **User ID Input Check (Optional Improvement):** `p_user_id` চেক করার আগে `IF p_user_id IS NULL OR p_user_id <= 0` কন্ডিশন যোগ করলে ইনভ্যালিড বা নেগেটিভ User ID দিলে আরও স্পষ্ট `'Invalid User ID.'` মেসেজ পাওয়া যাবে।
